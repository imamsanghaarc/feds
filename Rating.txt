--------------------------------------------------------------------------------
1. METHOD
--------------------------------------------------------------------------------

Step 1 - Define the rubric from the market, not from opinion. The criteria in
Section 4 are the dimensions that current industry guides and vendor
documentation use to judge whether an agent qualifies as an "AI employee"
rather than a chatbot.

Step 2 - Assemble a benchmark set of real products: Cursor (agents, cloud
agents, enterprise), Anthropic (Claude Code, Claude Cowork, Skills, Managed
Agents), and role-specific AI employees (11x, Artisan). Their documented
capabilities and controls are recorded in Sections 3 and 5.

Step 3 - Score FEDS per criterion against that rubric, weighting each
criterion by how much it contributes to a deployable, trustworthy AI
employee. Every score below names the evidence it rests on. Where the
repository itself declares something unproven, this review treats it as
unproven rather than as passing.


--------------------------------------------------------------------------------
2. THE RUBRIC: WHAT THE MARKET MEANS BY "AI EMPLOYEE"
--------------------------------------------------------------------------------

Current industry definitions converge on four technical tests plus three
operational tests:

  Technical:
    T1  Role      - scoped to a defined job with boundaries, not general Q&A.
    T2  Tools     - can take real actions in connected systems, not just answer.
    T3  Memory    - retains context and learns across sessions.
    T4  Initiative- chooses the next step within its role without being
                    micromanaged.

  Operational:
    O1  Governance - explicit boundaries on what it may do unattended, what
                     requires human sign-off, and how a mistake is detected
                     and reversed.
    O2  Escalation - a defined path to a human when it cannot complete a task.
    O3  Measurement - task completion and error rates are measured, not
                      asserted in marketing language.

The same sources name the standing risks this rubric is designed to expose:
confident mistakes at volume, underestimated oversight cost, and missing
governance boundaries. Those three risks are what Sections 7 and 8 check.

Anthropic's published agent-engineering guidance adds the architectural
criteria used here for build quality: keep the design simple and composable,
keep the agent's planning visible, and invest seriously in the
agent-computer interface (tool contracts and documentation). Its Managed
Agents architecture adds the modern security criteria: a durable append-only
session log kept outside the model's context window, and credentials kept
out of reach of the sandbox where generated code runs.

3. BENCHMARK SET RESEARCHED (what the reference products actually offer)
--------------------------------------------------------------------------------

CURSOR (Anysphere) - coding agents, reviewed from cursor.com product/docs:
  - Agents run locally or as Cloud Agents in isolated VMs with cloned repos,
    dependencies, secrets and network access; multi-repo support; artifacts
    (screenshots, video, logs); remote desktop control of the agent's machine.
  - Parallel agents; triggered from web, desktop, iOS, Slack, GitHub, Linear
    or API; automations for scheduled work.
  - MCP support on both HTTP and stdio transports with OAuth; repository
    hooks (pre/post tool, file, lifecycle) keep formatters and policy checks
    active in cloud runs.
  - Enterprise tier: SAML/OIDC SSO, SCIM, audit logs, service accounts,
    granular and group-level spend controls, repository/model/MCP access
    controls, auto-run/browser/network controls, team privacy settings.
  - Pricing observed 2026-10-19: Free $0; Plus $8/mo; Premium $30/mo (cloud
    agents and automations included); Super $100/mo; Ultra $200/mo;
    Teams $30+/user/mo; Enterprise custom. Cloud agent model usage is billed
    at API list price on top of the seat.

ANTHROPIC - Claude Code, Claude Cowork, Skills, Managed Agents, reviewed
from claude.com, anthropic.com and the engineering blog:
  - Claude Code: agentic terminal/IDE harness for software engineering.
  - Claude Cowork: hands off multi-step knowledge work across chosen folders
    and tools; runs on desktop/web/mobile; continues unattended when the
    laptop is closed; schedules recurring tasks; splits big projects into
    parallel chunks; built-in browser; connectors, plugins (skills +
    connectors + sub-agents bundled).
  - Governance: user chooses which folders/tools are reachable, deletion
    requires approval, permission settings make the agent show its plan and
    wait before significant actions; admins toggle access, set RBAC, manage
    spend limits; activity streams to a SIEM via OpenTelemetry; runs on
    Bedrock, Vertex AI or Microsoft Foundry for data residency.
  - Skills: packaged domain knowledge loaded on demand - the pattern FEDS
    implements independently.
  - Managed Agents (engineering, Apr 2026): session (append-only log),
    harness and sandbox decoupled so each can fail or be replaced
    independently; session log lives outside the context window and is
    re-read on resume; credentials are held in a vault and reached through a
    proxy so generated code never sees tokens; sandbox failure returns as a
    tool-call error rather than killing the session.
  - Pricing observed: Cowork on Pro $17/mo annual ($20 monthly), Max 5x
    $100/mo, Max 20x $200/mo; Team and Enterprise custom.
  - Published agent design principles: simplicity, transparency of planning,
    and rigorous tool documentation/testing (the "agent-computer interface").

ROLE-SPECIFIC AI EMPLOYEES (11x, Artisan, Lindy, Sintra, Agentforce,
Beam AI) - reviewed from vendor sites and independent 2026 guides:
  - Pattern: one agent per job (AI SDR, AI receptionist, AI support agent),
    connected to a narrow set of systems (CRM, calendar, phone, help desk),
    measured on outcome metrics (response time, resolution rate, reply rate).
  - 11x: "digital workers" for go-to-market - voice, email, chat, social and
    SMS agents over one shared context layer, with CRM/calendar/GitHub-scale
    integrations and enterprise trust pages.
  - Commercial shape: priced for teams (from seat subscriptions to five- and
    six-figure enterprise contracts), sold on measured outcomes.
  - Independent guidance consistently warns that the "employee" label is
    packaging: the technical differentiators that matter are tool access,
    memory, initiative, and - above all - governance boundaries and a human
    escalation path.

===================== SCORE-BY-SCORE EVIDENCE =====================

1. ROLE DEFINITION & SCOPE DISCIPLINE                          9.0 / 10
   FEDS has an unusually explicit identity contract: a named agent enforced
   by SYSTEM_PROMPT.md and asserted by tests, a written runtime contract
   (AGENTS.md), a frontend-only lane that refuses backend work while still
   defining a client interface contract, measurable quality targets (Core
   Web Vitals: LCP <= 2.5s, INP <= 200ms, CLS <= 0.1 at p75), and a
   deterministic snippet-vs-implement rule decided by size rather than verb.
   Evaluated cases show the scope holding under pressure (backend requests
   refused, raw SQL refused, no invented tool names). This is at or above
   the market standard for role definition - most commercial "AI employees"
   ship with a marketing description rather than an enforced behavioral
   contract.
   Deduction: the contract is enforced by prompt plus offline tests, not by
   a runtime capability boundary, so scope ultimately depends on model
   compliance.

2. ACTION SURFACE (TOOLS / MCP)                                 8.0 / 10
   Ten scoped MCP tools over Neon with a clear contract: task library
   (lookup/list/find_similar/save/record_review/publish) and memory layer
   (save/list/delete/promote). Reads are free; writes are gated; there is no
   generic SQL tool; each call writes an audit row and a capability metric.
   This matches Anthropic's guidance to treat tool design as first-class
   work, and it is stronger than the average agent integration, which tends
   to expose broad CRUD.
   Deduction: narrow by construction. No code execution, no browser, no
   repository or CI access, no messaging/ticketing integrations. FEDS can
   reason about frontend work and record it, but it cannot itself open a PR,
   run a build, or screenshot a page - things both benchmark platforms do.

3. MEMORY & CROSS-SESSION LEARNING                              9.0 / 10
   The strongest part of the system, and above the market norm:
   private per-user memory isolated in SQL (not in application filters),
   three automated promotion gates (recorded verification, a generalizable
   flag with project-specific refused, and a sanitized rewrite that blocks
   identity, credential-shaped text, fenced code, source lines, JSX and
   local paths), an append-only shared layer enforced by a database trigger
   with provenance columns, promotion approval as the only human step, and
   fail-closed behavior when identity is missing. The raw private body never
   leaves the private layer. Verified live by zero-quota smoke tests
   (cross-user reads refused, every gate fired, restriction role proven).
   Deduction: learning is retrieval-only. The Verified Lesson Loop design
   (confidence dynamics, quarantine, duplicate/contradiction detection,
   holdout lift measurement, consolidation and rollback) is specified but
   not built, so FEDS stores lessons without yet measuring whether they
   improve outcomes.

4. KNOWLEDGE SKILLS & CONTEXT ECONOMY                           9.0 / 10
   35 skills in the standard .claude/skills/ location shared by Claude Code,
   OpenCode and the SDK, with a tested fallback path; progressive disclosure
   carrying an ~11,400-character index instead of an ~100,700-character
   corpus - an 88.6% reduction in context cost per turn; tolerant loading
   that degrades gracefully rather than crashing a turn; skills composed
   through handoffs; reference material loaded on demand. Trigger eval
   11/11 with false-positive checks passing. This is the same pattern
   Anthropic now ships as a product capability (Skills), implemented here
   independently and with an explicit measurement of the context saving.
   Deduction: single-sample trigger evidence, and in 10 of 11 cases the
   correct selection was reported rather than proven by a recorded load.

5. AUTONOMY & TASK EXECUTION BREADTH                            6.0 / 10
   FEDS runs a competent single-session loop: load skill, work, call tools,
   return a fixed four-heading answer, pause at approval gates, resume on
   decision. It is a workflow-with-judgment system, close to what Anthropic
   calls the augmented-LLM-plus-tools pattern.
   Deduction against the market: no parallel sub-agents, no scheduled or
   recurring unattended runs, no long-horizon session management
   (compaction/resume of a durable session log outside the context window),
   no execution sandbox for generated code, no browser or computer use.
   Cursor's cloud agents and Anthropic's Cowork both offer parallel,
   unattended, environment-backed execution; 11x runs continuously across
   channels. On breadth of autonomous execution, FEDS is a single-threaded
   CLI agent and scores accordingly.

6. HUMAN OVERSIGHT & APPROVAL CONTROL                          8.5 / 10
   Approval-gated writes (publish_task, promote_memory) pause the run,
   persist state in run_states so a restart cannot lose a parked approval,
   resume only through a decision CLI, enforce an operator allowlist
   case-insensitively, audit refusals as approval_refused with a non-zero
   exit, hold a per-conversation advisory lock so two operators cannot
   interleave decisions, and require a separate opt-in for production
   publication. Reads remain free. This implements the "autonomy slider"
   that commercial platforms advertise, at the level of individual actions,
   and the operator-authorization layer is more explicit than most.
   Deduction: the gate lives in the worker process, not in the database -
   the repository itself documents that the runtime role could still write
   a well-formed shared row directly, and defers the fix. Approvals are
   CLI-only; there is no console or notification surface, so the human step
   is engineered well but is not yet operable by a non-developer.

7. SECURITY & TRUST BOUNDARIES                                 8.5 / 10
   Evidence-backed strengths: a least-privilege runtime database role
   (no DDL, no ownership, no admin) proven by a live privilege smoke test;
   an offline test that fails the build if runtime DDL reappears in either
   process; a planted-secret scanner that fails the build on credential
   patterns in committed files; credentials in a gitignored .env consumed
   through one config module; fail-closed identity with no shared-bucket
   fallback; MCP defaults to stdio and refuses a non-loopback bind so the
   approval gate cannot be bypassed over the network; append-only shared
   memory; a deliberately narrow input guardrail (only trust-boundary
   subversion is hard-blocked) with two pinned tests proving both sides;
   pasted content treated as data by the prompt rather than executed.
   The narrow guardrail is the correct design, not a weakness - it is
   documented with the reasoning and regression-pinned.
   Deductions: approval is not database-enforced (see 6); container
   deployment artifacts were reviewed but never executed; secrets rotation
   is still open before any external sharing; unlike Anthropic's Managed
   Agents there is no credential vault/proxy isolation from generated code,
   because FEDS does not execute generated code at all (that reduces the
   exposure but also the capability).

8. OBSERVABILITY, AUDIT & COST HONESTY                          8.5 / 10
   A closed audit vocabulary where the schema's CHECK constraint is the
   source of truth (a test reads the write sites so the code cannot emit a
   verb the database would reject), audit rows written by both processes,
   full conversation replay from audit_log alone, per-turn token and cost
   rollups with cost_basis labelled as an estimate, unknown pricing left
   NULL rather than reported as zero, latency and outcome metrics per tool
   call, and persisted sessions. This is a genuine differentiator: many
   commercial agents expose only vendor-side transcripts.
   Deductions: no dashboard, alerting, or streaming export - no equivalent
   of Cursor's audit logs or Anthropic's OpenTelemetry-to-SIEM path, so the
   trail is analyst-readable via CLI but not operationally monitored.

9. EVALUATION RIGOR & EVIDENCE QUALITY                          7.5 / 10
   Process quality is high and rare for a project this size: an offline
   suite of 3 suites run before any push, resumable eval harnesses with
   exit-code discipline (an incomplete run cannot pass as a clean run),
   ground truth taken from recorded tool calls rather than from the agent's
   own claim, false-positive cases in the trigger eval, zero-quota smoke
   tests so verification survives provider exhaustion, and a documented
   correction that removed previously fabricated eval results and explains
   the tells that exposed them. That correction is a mark of maturity.
   Deductions, all self-declared: the trigger eval is 11/11 as a single
   sample per case with only 1 pass backed by a recorded load; the
   system-prompt eval is 8/8 run with 6 passing before two real fixes whose
   live re-verification is pending quota; the three-runs-per-case stability
   pass is open. No stable behavioral rate has been measured yet, and this
   review does not claim one.

10. PROVIDER RESILIENCE & MODEL FLEXIBILITY                    7.0 / 10
   Quota-aware rotation on 429/402 only, with cooldowns and a maximum wait;
   a genuine failover to a second credential was observed live on
   2026-10-19; chat and embedding routes are separate with a test forbidding
   a chat-only provider from appearing in the embedding order; the fallback
   credential serves the same model so stored vectors stay comparable;
   model-scoped search with a 768-dim HNSW index; re-embedding tooling with
   dry-run/dedupe/orphan purge; a provider status probe; and rejected
   credentials deliberately propagate instead of being routed around.
   Deductions: both live credentials are Gemini, so a shared upstream
   (same project quota) remains a single point of failure; OpenAI is
   disabled; there is no local embedding fallback, so ingestion and search
   require the network; no Anthropic or other family is wired in. Benchmarks
   run multi-provider fleets by default.

11. INTEGRATION, PORTABILITY & ECOSYSTEM                       6.5 / 10
   Real portability: MCP over stdio is the open protocol standard;
   skills live in a directory format shared by Claude Code, OpenCode and the
   SDK; the whole system is one Python repository run with uv, no build
   step; bulk ingestion normalizes arbitrary reference material into the
   knowledge base idempotently.
   Deductions: no connector marketplace, no Slack/GitHub/Linear/CRM
   integrations, no API or web surface for other people to drive it, no
   mobile or chat entry point, and web search is excluded by explicit
   decision. Commercial AI employees are defined by their integrations;
   FEDS currently integrates with one database and a filesystem.

12. DEPLOYMENT, SCALE & ENTERPRISE READINESS                   4.5 / 10
   Present: Dockerfile, compose.yml, .dockerignore and a deployment
   reference covering connection pooling, provider resilience and secret
   hardening.
   Missing or unproven: containers were never executed in this environment;
   no restart supervision, rate limiting or backpressure under load; a
   single process with no horizontal scaling or parallel agent execution;
   no SSO/SAML, SCIM, role-based access control beyond a local operator
   allowlist, no spend caps, no repository/model access controls, no
   audit-log export or SIEM integration, no multi-tenant administration.
   Every one of these exists in the benchmark products' enterprise tiers.
   Until the container is run once and supervision exists, this is the
   category that most limits production deployment, and it is the reason the
   overall rating sits below 8.0.

Where FEDS leads the benchmark set: memory promotion governance, database-
level least privilege with proven refusals, a schema-constrained audit
vocabulary, and approval semantics that persist across restarts with

--------------------------------------------------------------------------------
6. STRENGTHS (at or above market)
--------------------------------------------------------------------------------

  - Memory architecture with three automated promotion gates, sanitization,
    append-only shared storage, provenance, and fail-closed identity. Above
    the norm for both commercial AI employees and open-source agents.
  - Least-privilege runtime database role with a live proof that DDL is
    refused, plus a test that keeps runtime DDL from returning.
  - Approval gates that survive restart, authorize the decider, refuse and
    audit unauthorized attempts, and lock against concurrent decisions.
  - Audit trail as a database-enforced closed vocabulary, replayable to a
    full conversation, with honest cost accounting (NULL when unknown).
  - Progressive disclosure of 35 skills with an 88.6% measured context
    reduction and a trigger eval that found and fixed real defects.
  - Evaluation governance: fabricated historical results were removed,
    documented, and guarded against; incomplete runs cannot pass as clean.
  - Provider failover proven against a real quota failure, with rotation
    deliberately limited to quota exhaustion so real bugs stay visible.
  - Zero operating license: the only costs are model tokens and the
    database, versus $30-$200 per seat per month for the benchmark tools.


--------------------------------------------------------------------------------
7. GAPS AND RISKS (below market)
--------------------------------------------------------------------------------

  - Execution breadth: no parallel agents, no scheduled unattended runs, no
    sandboxed code execution, no browser. An AI employee that must be asked
    once per task and cannot verify its own work in a running environment
    covers a fraction of what the benchmark products cover autonomously.
  - Enterprise controls: no SSO, SCIM, RBAC beyond a local allowlist, spend
    caps, telemetry export or SIEM integration.
  - Deployment unproven: container artifacts never run; no supervision,
    rate limiting or backpressure.
  - Provider concentration: both live credentials are one vendor family;
    no local fallback for embeddings.
  - Evidence strength: no stable behavioral rate has been measured. The
    11/11 and 6/8 figures are point measurements, as the repository states.
  - Approval is worker-enforced, not database-enforced - documented as
    deferred, and the single most important item to close before any
    high-consequence write path is exposed.
  - Single-operator ergonomics: approvals are CLI-only; no console,
    notifications or review surface for non-developers.


--------------------------------------------------------------------------------
8. VERDICT
--------------------------------------------------------------------------------

FEDS scores 7.7 / 10 as an AI employee.

It is, in the market's own terms, a genuine AI employee: it has a defined
role, real tools it can act with, cross-session memory that learns, and
initiative within its boundaries - and it clears the operational bar that
most marketed "AI employees" do not, because its governance, audit and
memory-promotion rules are enforced in code and in the database rather than
described in documentation. On governance craftsmanship it compares
favorably with products charging $30-$200 per seat per month.

It is not yet a production-grade employee at the level of the benchmark
platforms, for three concrete reasons rather than any judgment about its
design: it cannot execute and verify work in a real environment (no sandbox,
browser, parallelism or scheduling); it has no enterprise administration
surface (SSO, RBAC, spend controls, telemetry export); and its deployment
path and behavioral statistics are both unproven - the container has never
been run, and no eval has been measured across repeated runs.

Trajectory matters for a rating: the gaps in Section 7 are all recorded,
owned and prioritized in the repository's own backlog, and none of them
require rearchitecting. Closing the container run, the stable-rate evals,
provider-family diversity and database-enforced approval would, on this same
rubric, move FEDS into the 8.0-8.5 band. Adding execution breadth
(sandboxed verification, scheduled runs, parallel work) is what would make
it competitive with the benchmark platforms rather than merely governed as
well as they are.

  OVERALL WEIGHTED RATING: 7.7 / 10 - solid, well-governed, and honest about
  what it has not yet proven; constrained on autonomy breadth, integration
  surface, and enterprise readiness.
